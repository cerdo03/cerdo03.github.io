KV-Cache Internals

Module 1 showed why a KV cache saves work during generation. This lesson opens the cache: which tensors it holds, what shape they have, when each entry is written, and which computation it removes (and which it does not).

Learning goal: after this lesson you can state exactly what a KV cache stores per layer and position, write its conceptual shape, trace one decode step from input token to appended cache entry, and count the projection work a cache avoids while attention work still grows.

Running example: the 4-token prompt The sky is blue, followed by a fixed toy continuation and the sun shines .. Here “blue” is already part of the supplied prompt, so it is cached during prefill. The first new answer token is “and”. The trace uses the shared 2-component starting embeddings for The/sky/is and the same projection matrices as Lessons 1 and 2.1; other token embeddings are fixed invented values. This is a 1-layer, 1-head toy.

2.4.1 What exactly is cached?

The KV cache stores each processed position’s key and value vectors, separately for every layer and KV head. Later tokens read these stored vectors instead of recalculating them. The current query is used to calculate the current attention result; old queries and attention weights are not stored in the KV cache.

The cache holds keys and values, per layer, per position

  • K and V for every processed position, in every attention layer. Each layer has its own WK, WV and its own input x, so each layer has its own cache entries. With grouped-query attention (Lesson 2.3) each entry has HKV key heads and HKV value heads.
  • Queries are not cached. In causal decoding a new token is always appended at the end. Later tokens never ask an old position to attend again, so a past query qi is never needed after its own forward pass. Old keys and values, in contrast, are read by every later query.
  • Numeric tensors, not token IDs. An entry is a block of floating-point numbers (for example fp16/bf16), the output of a projection. Storing token IDs would force the model to recompute every layer to get K and V back, which is the work the cache exists to avoid.
  • Tied to position and the entire prefix. In layer 0, xi depends on the token and its position. In every deeper layer, xi is the output of earlier attention over the whole prefix 1…i. The same token in a different context therefore produces different K/V in layers above 0. A cache entry is only valid for the exact prefix that produced it.
  • Old entries are never recomputed when appending. Under a causal mask, appending token p cannot change any earlier position's inputs, so k1…kp−1 and v1…vp−1 stay exactly as computed.

RoPE (deeper topic). Many current models use rotary position embeddings: q and k are rotated by angles that depend on their positions just before the dot product, so their score depends on the relative offset. Values are not rotated. Implementations typically cache keys after rotation, so old keys never need re-rotating. Details vary by implementation and are outside this lesson; the toy model below does not model RoPE.

2.4.2 The conceptual shape of the cache

Collect the per-layer, per-position, per-head key vectors into one tensor, and the value vectors into another. For one sequence (no batch dimension):

Kcache, Vcache ∈ ℝL × T × HKV × D
L
number of attention layers (each has its own cache)
T
number of positions processed so far (grows by 1 per decode step)
HKV
number of key/value heads (equals the query-head count in MHA, 1 in MQA, in between for GQA)
D
head dimension, the length of one key or value vector

Read it as a hierarchy: the KV cache → one layer → its keys or values → one token position → an HKV × D slice. That slice is everything one position contributes to one layer's keys (or values).

Conceptual, not physical. This order is a way to reason about contents, not a universal memory layout. Hugging Face-style caches typically keep one tensor per layer shaped [B, HKV, T, D]; serving engines such as vLLM store K/V in fixed-size blocks (paged layouts), and attention kernels may require their own orderings. The planned Module 3 covers physical layouts. The element count is the same either way.

2.4.3 Building the cache during prefill

The prompt is fully known before generation starts, so prefill processes all of its positions in one parallel forward pass: K = XWK and V = XWV are single matrix multiplications over all 4 rows of X. The causal mask still applies inside that pass: position i scores only keys 1…i.

  1. All 4 positions compute q, k, v together; 4 key rows and 4 value rows are written to the cache.
  2. Each position attends under the causal mask (table above), giving 1 + 2 + 3 + 4 = 10 query–key scores.
  3. Only the last position's output goes on to the model head as next-token logits. Sampling from them gives the first output token.

Cache after prefill: 4 entries per layer (one per prompt position). The first sampled token is not one of them: it has not been through a forward pass, so it has no key or value yet.

2.4.4 Reusing the cache during decode

Each decode forward pass processes exactly one new position p, the token sampled at the end of the previous pass. For that position, in each layer:

qp = xpWQ, kp = xpWK, vp = xpWV
op = softmax(qp K0:pT / √d) V0:p, K0:p = [Kcache; kp]
p
zero-based index in these equations; equals the cache length before this pass. The tracer labels token positions starting at 1, so its label is p + 1
Kcache, Vcache
the p cached rows for positions 0…p−1, read, not recomputed
K0:p, V0:p
cached rows plus the new row: p + 1 keys and values
d
head dimension (2 in the toy)

The new query still has to be scored against all p + 1 keys: that is the attention work, and the cache does not remove it. What the cache removes is recomputing k and v for the p old positions.

    2.4.5 With versus without a cache

    Here is the same toy run counted pass by pass. Projected positions means the number of token positions whose K/V projections are computed in that forward pass, per layer (multiply by L for a full model). Without cache assumes each decode pass re-runs the whole sequence processed so far. No timings are shown: counts are exact, durations depend on hardware.

    Cumulative projected positions

    What changes and what does not

    • Avoided recomputation: with a cache each decode pass projects 1 position; without one, pass n projects T + n. Over n decode steps the cumulative projection count is O(n) with a cache and O(n2) without.
    • Remaining attention: the new token's query scores p + 1 keys either way, so attention score work for the new token is O(n) per step with or without a cache. (A full re-run without a cache would additionally recompute every earlier position's attention row.)
    • KV reads: the cache turns recomputation into memory reads: pass p reads p cached entries per layer. Lesson 2.5 turns this into bytes and bandwidth.
    • KV memory: the cache holds one entry per processed position per layer, growing linearly with sequence length.
