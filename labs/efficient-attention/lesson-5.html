Sharing safely; choosing an optimization

Preserve another request’s history while sharing storage, then choose optimizations from evidence.

A shared prefix can have two owners

Two continuations can begin with the same processed prefix. Their logical histories can reference the same physical K/V until a write requires private storage.

What you will be able to explain

Follow ownership through sharing, copy-on-write and release; distinguish prefix caching policy; choose an optimization from workload evidence.

Copy-on-write

Private tail
A block with one owner; that request can append without changing another sequence.

Fixture: A has six processed positions; C = 4. Fork B shares both blocks. A’s next processed token would write the shared partial tail, so reserve a destination, copy its two valid rows, remap A, then append.

Fork → detect shared tail → reserve → copy valid rows → remap → append → release. The first full block stays shared.

Allocator operations commit transactionally; the scene exposes conceptual stages inside that change. Reserved destinations are shown separately before remapping. GPU synchronization and instruction atomicity are not simulated.

Fork sharing and prefix caching are different policies

Fork sharing starts from a known shared processed history. Cross-request prefix caching needs a way to identify reusable computation and decide what stays resident.

Reusing a later word after a different earlier prefix is unsafe: K/V depends on model, position and preceding context. Check exact token prefix and compatible model/weights, positional settings, adapters and other conditioning. Do not assume equal strings alone establish reusable tensors.

Current vLLM prefix-cache documentation describes full-block reuse with prefix-dependent identity. A shared partial tail in the paper’s fork/COW example is not permission to reuse arbitrary partial blocks across requests.

A zero-reference block is reclaimed immediately in this module’s allocator. A prefix-cache policy may keep an unreferenced valid block eligible for reuse until eviction. “Unused by active requests” and “contains no cached data” are different states.

Name the resource before choosing the optimization

Attention kernels and serving cache managers cooperate. They address different costs, even when an engine combines both.

PagedAttention includes block-aware attention access; the cache manager controls allocation and sharing. More admitted requests can improve throughput opportunity but also alter latency. Neither phase names nor byte ratios establish measured speedup.

  1. Long prefill with large temporary score/probability arrays: investigate workspace/IO-efficient kernels.
  2. Ragged growing requests wasting reserved capacity: investigate allocation/slack.
  3. Repeated compatible prefixes: investigate valid-prefix reuse.
  4. One long decode request: measure context-read traffic and kernel behavior; paging alone does not remove it.

    new_m = max(m, max(scores))
    alpha = exp(m - new_m) if denominator else 0
    p = exp(scores - new_m)
    denominator = alpha * denominator + sum(p)
    numerator = alpha * numerator + p @ values
    m = new_m
output = numerator / denominator
