GPU execution

Trace a projection from mathematical work to logical threads and physical resources.

One equation, many independent outputs

For a projection, U [rrows × kinner] multiplies weights W [kinner × ccols] to produce Y [rrows × ccols]. Each output is a dot product. Different outputs can be computed independently once the inputs exist.

Y[irow, jcol] = Σ over psum from 0 to kinner − 1 of U[irow, psum] × W[psum, jcol]. Here irow selects a row, jcol a column, and psum walks through the shared width.

Work groups and hardware

A kernel is a GPU function launched to do a task. A grid is the collection of blocks in that launch. A thread is one logical instance of the function; in this example, it computes one output element.

A block is a group of threads that can share temporary storage (shared memory) and wait for one another at synchronization points. “128 threads per block” means grouping the output work into groups of 128. A block is a work group, not a physical processor.

An SM (streaming multiprocessor) is a hardware unit on an NVIDIA GPU that executes threads from assigned blocks. A warp is a group of 32 threads within a block; a lane is a thread’s position within its warp, numbered 0–31. One SM can host multiple blocks. The explorer separates this hardware placement from the grid’s logical grouping.

For the mapping below, ceil means round up: any leftover outputs need another block. A guard checks whether a thread’s output index is in range before it loads inputs or stores a result.

Follow one output through the hardware

Plain version: a thread is one worker that computes one output number. A warp is 32 workers that move through instructions together. A block is a team of threads that can share scratch memory. An SM is the chip unit that runs blocks. Only the SM is physical hardware; the other three are bookkeeping that groups work.

Follow one output number

Example: output 999 of 1,000, with 128 threads per block. It is thread 103 of block 7, in warp 3, lane 7. Block 7 runs on one SM; the model does not pick which one.

Map work onto a GPU

Example: 1,000 output elements with 128 threads/block need 8 blocks. The last warp has 8 valid output lanes and 24 guarded lanes. A block stays on one SM during ordinary execution; a warp contains 32 CUDA threads.

Indexing pseudocode and scheduling details

A thread is not a dedicated physical core. Ready warps can issue instructions while others wait on dependencies. Blocks need not start together or execute in numerical order. This ordinary mapping keeps a block on one SM; it does not specify which SM or when it runs.

// Schematic mapping, not an optimized CUDA GEMM.
flat = blockIdx.x * blockDim.x + threadIdx.x;
if (flat < rows * columns) {
    row = flat / columns; col = flat % columns;
    acc = 0;
    for (p = 0; p < reduction; ++p)
        acc += U[row][p] * W[p][col];
    Y[row][col] = acc;
}

The multiply-add loop has an accumulator dependency. Parallel output elements do not eliminate that dependency. Optimized kernels distribute work differently and can use tensor cores for matrix fragments; this one-thread-per-output sketch explains indexing only.

Enough work is not enough resources

A block needs registers and shared memory to reside on an SM. A larger block or more storage per block can reduce how many warps are resident. More resident warps may help hide latency, but occupancy alone does not measure useful throughput.

Resident means currently allocated space on an SM, whether ready to run or waiting. Registers hold a thread’s working values, such as its running sum. Shared memory holds values cooperating threads in one block can reuse. Both have limited space.

Occupancy is the resident warp count divided by the SM’s maximum resident warp count. The toy SM below has 64 warp slots: 8 resident warps means 8 / 64 = 12.5% occupancy. This counts allocated warps, not how busy they are. KiB means 1,024 bytes; each 32-bit register holds 4 bytes.

Change one resource limit

Toy SM: 2,048 resident threads, 65,536 32-bit registers, 64 KiB shared memory, at most 8 blocks. With 128 threads/block, 64 registers/thread and 32 KiB/block, shared memory limits residency to 2 blocks (8 warps, 12.5% occupancy).

Why this is only a residency upper bound

Limits are invented and independently rounded for teaching. Real occupancy includes allocation granularity, architecture-specific limits and compiler decisions. The diagram ignores scheduling policy, issue width, instruction latency and register spilling. Insufficient blocks in the grid can leave SMs idle even when resource occupancy is high.

Registers hold per-thread state such as the accumulator. More registers can avoid spills or enable reuse; reducing them blindly can add device-memory traffic. Search for a causal trade-off, not maximum occupancy.

Parallelism must respect dependencies

In “The sky is”, prefill has three supplied token rows. Within one layer, many projections and output elements can run in parallel. The next layer still needs the previous layer’s outputs. During ordinary autoregressive decode, the next input token is unknown until the current step selects it.

Known inputs → projection gridMany independent dot products across rows and columns.
Attention and remaining layer workDependencies within the layer still apply. Causal masking prevents future-token information flow.
Next layer → logits → selectionOnly after selection can the new token become the next input.

These are data dependencies, not a GPU scheduling trace. A transformer head is not an SM, a token is not a thread, and one layer is not necessarily one kernel.

A branch chooses a path, such as the true or false side of an if. If lanes in one warp choose different paths, this is divergence: each path runs with only its participating lanes active. An active lane mask records which lanes participate; branching does not create another warp.
