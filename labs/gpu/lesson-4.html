Arithmetic intensity and roofline

Predict a limiting resource from units and assumptions, then ask what could falsify the prediction.

How much work per byte?

Arithmetic intensity connects a workload to a memory boundary. Count floating-point operations F and transferred bytes E, then divide. Always name whether those bytes cross HBM, L2, shared memory or another boundary.

I = F / E · units: FLOP/byte.
Example: 128 FLOPs / 320 bytes = 0.4 FLOP/byte for the tile-side-2 logical traffic from 3.3.

That 0.4 is not automatically an HBM intensity: cache hits can remove HBM reads. Below we explicitly assume bytes fetched from or written to device DRAM, using an optimistic one-read input/weight model. Compare analytical counts with hardware counters before calling it measured intensity.

Best-case projection traffic

For U [rrows × kinner] times W [kinner × ccols], F = 2rrowsccolskinner. If each input and weight is fetched once from DRAM and each output is written once, E = element bytes × (rrowskinner + kinnerccols + rrowsccols). This is an optimistic cold-data traffic assumption, not a promise that any kernel achieves it. Repeated loads can increase it; data already in cache can reduce it. Bias, old-output reads, conversions and workspace are excluded.

Two resource bounds, one roof

If a device sustains at most P FLOP/s and BW byte/s, execution needs at least enough time for both resources. With ideal overlap, the larger resource time is the lower bound. Real time can be much larger.

time ≥ max(F/P, E/BW)
attainable FLOP/s ≤ min(P, BW × I)
ridge intensity = P/BW

Compute throughput is arithmetic work per second; memory bandwidth is bytes moved per second. Here 1 TFLOP/s means 10¹² FLOPs per second, and 1 TB/s means 10¹² bytes per second. A millisecond (ms) is one thousandth of a second.

The ridge is where the compute and bandwidth roofs meet. Below its intensity, the model is bandwidth-bound: moving bytes sets the larger time bound. Above it, the model is compute-bound: arithmetic sets the larger bound. At the ridge the two bounds are equal.

The chart uses logarithmic axes: each labeled tick is ten times the previous one, rather than a fixed amount larger. Its point sits on an ideal roof, not a measured result. The controls change a hypothetical device; they do not change real hardware.

Move a projection across the roofline

Hypothetical dense device: 100 TFLOP/s, 1 TB/s; ridge = 100 FLOP/byte. One row of a 4096×4096 two-byte projection has intensity about 1 FLOP/byte. With 512 rows, intensity is 409.6 FLOP/byte under the stated one-read assumption. No device is benchmarked.

Precision choices and limits of the roofline

Divide FLOPs by FLOP/s to obtain seconds, then multiply by 1,000 for milliseconds. Do not mix GB/s and GiB/s. Count a multiply-add as two FLOPs consistently in work and device throughput.

Select a ceiling matching precision, matrix instructions and dense versus sparse work. A sparse advertised tensor-core peak cannot be used as a dense FP32 ceiling. The sliders describe a hypothetical device, not any released GPU; changing storage bytes holds compute ceiling fixed for comparison, whereas real hardware often changes compute rates with precision.

Near the ridge both resources matter. A point below both ceilings may be limited by launch latency, dependency chains, occupancy, shape, synchronization or another memory level. A roofline label is a hypothesis about a chosen operation and boundary, not proof of the actual bottleneck.

A prediction you can disprove

Suppose the model says memory time dominates. Predict that reducing transferred bytes will matter more than raising peak math rate. Then try to disprove that prediction: if traffic falls but runtime does not, inspect the next limit.

  1. Fix the tensor shapes, precision, operation and memory boundary.
  2. Calculate work and traffic; state cache/reuse assumptions.
  3. Change one cause: rows, tile size, layout or bytes per value.
  4. Compare result correctness, measured time and transferred bytes.
  5. Explain disagreement; do not relabel the graph as a benchmark.

Without GPU access, complete steps 1–3 and write expected outcomes. Leave measured time and counters explicitly “not measured”. A CPU experiment can validate correctness and counting logic; it cannot establish CUDA performance.
