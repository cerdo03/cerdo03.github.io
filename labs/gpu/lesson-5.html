Prefill, decode and evidence

Use what changes between phases—row reuse and KV reads—to form workload-specific hypotheses.

Prefill and decode change matrix shapes

For one projection, flatten the tokens processed in this step into rrows rows. Prefill may contribute many supplied token rows. Ordinary decode usually contributes one row per active sequence. More rows can reuse the same weights across more useful work.

Active sequences are the separate requests processed together in this step (the batch). A prefill chunk is the group of supplied tokens processed per sequence in this step. Equal-length prefill chunks give rows = active sequences × chunk tokens; ordinary decode contributes one row per active sequence. The chunk control applies only to prefill. These are projection rows, not the number of cached positions read by attention.

Change phase, batch and chunk length

One 4096×4096 projection with two-byte elements: one decode sequence gives r=1, while prefill with one 512-token chunk gives r=512. Batch 512 ordinary decode also gives r=512 for this projection, although its attention and scheduling costs differ. Neither phase name determines its bottleneck.

The shape argument, not a universal rule

Ragged batches (sequences with different processed lengths) sum the actual token rows. The projection uses the same optimistic one-read traffic model and dense FLOP convention as 3.4.

Attention has a different shape. For a full causal prefill with T positions and no earlier cache, each query position sees its prefix. Allowed query–key pairs per head total T(T + 1)/2. For three positions in “The sky is”, that is 1 + 2 + 3 = 6 pairs. One decode query over three visible positions has only 3 pairs per head. QK plus weighted-V work is about four FLOPs per pair per head component, excluding normalization. Some implementations execute masked work too; the pair count alone does not establish actual instruction count.

For a prefill chunk, count its query rows against both earlier cached positions and its own causal prefix. Longer context can change attention cost even when the projection row count is fixed. This explorer models projection reuse only; the next concept isolates decode KV reads.

A long prefill projection often has enough rows to reuse weights efficiently; small-batch decode can stream many weights for little work. Short prefill, poor shapes, quantization, cache residency, large decode batches, speculative decoding, fused kernels and hardware choice can change the balance. Full-request latency also includes attention, normalization, sampling, launch overhead, scheduling and communication. Do not add this single projection’s bound and call it a measured token latency.

Cached does not mean free to read

KV caching avoids recomputing earlier representations. Dense decode attention still reads keys and values for the context. Longer context and more sequences increase that read demand. GQA reduces the stored KV payload, while several query heads still need their own scores and outputs.

Visible positions are the context positions this query can attend to, including the current consumed position in this model. Read payload counts K/V bytes consumed this step; append counts the new K/V row written to the cache. They are separate quantities.

The explorer assumes perfect reuse of each KV head’s data across its query heads. Its work counts query–key dot products and weighted-value sums; its byte count excludes queries, outputs, softmax and other traffic. “KV-read-only intensity” is work divided by just that KV read payload, not the intensity of the whole attention operation. Capacity measures stored bytes; traffic measures bytes read or written during a step.

Count one layer’s decode attention

For one sequence, 4096 cached positions, 32 query heads, 8 KV heads and width 128: raw K+V reads = 2×4096×8×128×2 = 16,777,216 bytes (16 MiB). QK plus weighted-V work ≈ 4×4096×32×128 = 67,108,864 FLOPs; optimistic KV-read-only intensity = 4 FLOP/byte.

Accounting contract

For N sequences of T visible positions, Hq query heads, HKV KV heads and width D, count 4NTHqD FLOPs for QK and weighted V. This excludes softmax, scaling and other attention operations. Read payload = 2NTHKVDB bytes at the selected storage precision. Count current K/V append separately: 2NHKVDB.

Some kernels use the current position’s newly computed K/V directly. Actual DRAM traffic depends on the kernel, cache residency, layout and reuse; the idealized payload need not equal physical reads. Scores, metadata, scale factors and intermediate traffic are also excluded. Multiply payloads across layers only when configurations match; this explorer counts one layer.

From understanding to an original question

Choose a narrow mechanism, predict a change, then gather evidence that could reject it. “Make inference faster” is too broad; “does the KV-head layout cause redundant memory reads for this shape?” can become an experiment.

A CPU/Mac-friendly investigation

  1. Pick one projection shape and one decode-attention configuration from the explorers. Write all dimensions and units.
  2. Predict separately what happens when you double batch, double context, or reduce KV heads. Say which operation should change and why.
  3. Use the tiny scalar product from 3.3 as a correctness reference. Check that your alternative returns the same output before discussing speed.
  4. Record assumptions and expected outcomes. Mark hardware results “not measured” until a real device run exists.
When GPU access becomes available

Record GPU model, precision, kernel/library versions, exact shapes, batch, context, warmup and cache policy. Synchronize device work or use device timing events; asynchronous host dispatch time is not kernel time. Repeat runs and report variation. Compare outputs with a stated tolerance, then inspect achieved throughput, DRAM bytes/bandwidth and launch overhead with a profiler. Do not infer traffic solely from tensor size.

Example hypothesis: increasing projection rows improves weight reuse until compute or another limit takes over. A failed prediction is useful evidence: look for repeated loads, poor tiling, cache effects or insufficient parallelism. No paid hardware or cloud account is needed to finish these lessons.
