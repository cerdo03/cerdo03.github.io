Matrix multiplication and tiling

Keep the answer fixed. Change how many times an operand has to travel.

One output, four products

Use a tiny invented projection: U [4 × 4] times W [4 × 4] gives Y [4 × 4]. Select an output cell. Reveal each product and accumulate it. Inputs here are illustrative numeric rows, not the learned embeddings from Module 2.

A dot product multiplies matching entries from a row and a column, then sums the products. An accumulator is that running sum. Each multiply-add adds one product to it. One FLOP is one floating-point arithmetic operation; we count a multiply-add as two FLOPs, even when one fused instruction performs it.

Inspect products and sums

Y[0,0] = 1×1 + 2×0 + 0×2 + 1×1 = 2. Changing output cell changes the selected row and column. A fused multiply-add counts as 2 FLOPs even when implemented as one instruction.

Notation → dimensions → loops

Y[irow,jcol] = Σ over psum of U[irow,psum] × W[psum,jcol]. The reduction has kinner terms. There are rrows × ccols outputs. Conventional GEMM accounting uses F = 2rrowsccolskinner FLOPs (one multiply-add per term), even though a mathematical dot product needs only k − 1 additions if initialized from its first product.

for row in range(rows):
    for col in range(columns):
        acc = 0
        for p in range(reduction):
            acc += U[row][p] * W[p][col]
        Y[row][col] = acc

For the tiny example: 16 outputs × 4 terms × 2 FLOPs = 128 FLOPs. This scalar loop is a reference calculation, not a tensor-core implementation.

Load a tile, reuse its operands

Instead of independently reloading each dot product’s operands, compute a btile × btile patch of outputs together. One input tile and one weight tile supply many products. Tile size changes data reuse without changing the mathematical result.

A tile is a small rectangular portion of a matrix. The control chooses a square tile’s side length in elements. A reduction chunk covers part of the shared inner dimension: load two operand tiles, add their products to the output accumulators, then continue with the next chunk. The accumulators retain earlier partial sums until every chunk is complete.

Walk through load → barrier → reuse — follow exact partial sums and see when shared tiles are safe to overwrite.

Count work versus movement

For 4×4 matrices with 4-byte elements: tile side 1 issues 128 operand element loads plus 16 output stores = 576 bytes. Tile side 2 issues 64 loads plus 16 stores = 320 bytes. Tile side 4 issues 32 loads plus 16 stores = 192 bytes. These are logical global-memory demands under the teaching algorithm, not measured HBM traffic.

Derive the traffic and storage

For square tiles whose side btile divides all dimensions, there are (rrows/btile)(ccols/btile) output tiles. Each streams kinner/btile pairs of input tiles. Each pair holds 2btile² elements. Total operand loads = 2rrowsccolskinner/btile. Add rrowsccols output stores, then multiply by element bytes.

Two single-buffered input tiles consume 2btile² × element bytes in shared memory. Accumulators also need registers. Doubling btile increases this shared storage fourfold; double buffering would consume more. Our model omits caches, padding, spills, synchronization cost and traffic between shared memory and registers. It assumes the old output is not read (GEMM beta = 0).

for each output_tile:
    accumulators = 0
    for each reduction_tile:
        cooperatively load U_tile and W_tile
        block_barrier()
        accumulate products into registers
        block_barrier()  // finish before overwriting tiles
    store output_tile

Predict: A larger tile always runs faster?

Why this matters for attention

Attention also multiplies matrices. Materializing a full score/weight matrix in device memory can add substantial traffic. A fused, tiled algorithm can avoid storing that full intermediate there while preserving the attention computation.

Separate operationsScore matrix → write intermediate → read it for normalization/value mixing.
IO-aware tiled attentionBring in blocks of keys/values, update an output accumulator and normalization state, avoid a full device-memory score matrix.

This is the motivation behind FlashAttention, not its complete algorithm. Online softmax must update running normalization correctly; merely tiling ordinary softmax independently would change the answer. Exact attention here refers to the algorithm, not bitwise-identical floating-point results.
