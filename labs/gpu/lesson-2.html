Memory and movement

A GPU cannot compute with bytes that have not arrived. Track the path, scope and reuse of one operand.

Where an operand lives

A value stored in global memory must reach an execution unit before it contributes to a dot product. Storage capacity tells you what fits; traffic tells you how many bytes cross a boundary. They answer different questions.

Follow one operand

Illustrative tiled path: device memory (often HBM on datacenter GPUs) → cache lookup → block-shared scratchpad → per-thread registers → multiply-add → output store. Not every load uses shared memory. Registers and shared memory are on-chip; L2 is a device-wide cache, not the KV cache.

Memory scopes and limits
  • Registers: per-thread program state on the SM. Excess demand can spill into thread-local memory backed by device memory.
  • Shared memory: explicitly managed storage used by cooperating threads of a block; bank conflicts and synchronization affect its cost.
  • L1 / L2: hardware-managed caches. L1 is associated with an SM; L2 is shared across the device. Details vary by architecture.
  • Global address space: accessible to the kernel’s threads. Device storage may be HBM or another DRAM technology. A global load may hit cache and never fetch HBM.

A transformer KV cache is a software data structure, usually stored in global memory. Its name does not imply that it fits in hardware L2. Apple unified memory changes the physical organization; these capacity/traffic distinctions still help, while CUDA block and warp details do not transfer verbatim.

Neighboring lanes, neighboring addresses

If adjacent lanes request nearby addresses, hardware can service them with fewer memory sectors. Change the address stride before predicting how much useful data each sector carries.

Inspect a warp’s memory requests

Toy transaction model: 32 lanes each load one distinct 4-byte number; 32-byte aligned sectors, no cache reuse. Stride 1 from byte 0 touches 4 sectors (128 bytes); stride 8 touches 32 sectors (1,024 bytes) for the same 128 useful bytes.

Define the boundary before counting

This explorer counts distinct 32-byte sectors touched by one warp instruction. It does not predict HBM transactions, cache hit rate, latency or speedup. Real transaction rules depend on instruction width, alignment and GPU architecture. The byte offset changes alignment; stride is measured in elements, not bytes. The requested addresses remain distinct in this example.

Reusing bytes takes coordination

Several threads can reuse an operand loaded into shared memory. They must wait until the cooperative loads finish, then wait again before overwriting a tile still in use. Faster memory without correct synchronization is a race, not an optimization.

Cooperative loadThreads load different tile elements into block-shared storage.
Block barrierEnsure all required values are available before consuming them.
Reuse, then barrierAccumulate with the tile. Ensure consumers finish before the next tile overwrites it.

Ordinary block barriers must be reached by all participating threads consistently. Guard out-of-range loads and stores, not the barrier itself. Separate blocks cannot use an ordinary block barrier to communicate.

Capacity, traffic, bandwidth, latency

Capacity uses bytes; bandwidth uses bytes/second; latency uses seconds per dependent access. A 1 GiB tensor read ten times can create about 10 GiB of logical reads while occupying only 1 GiB. Hardware caches may reduce HBM reads. Shared-memory reuse can reduce global-load demand while consuming scarce on-chip storage. Lower HBM traffic does not guarantee lower time when another resource becomes limiting.
