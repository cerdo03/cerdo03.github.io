Memory and movement

A GPU cannot compute with bytes that have not arrived. Track the path, scope and reuse of one operand.

Where an operand lives

A value stored in global memory must reach an execution unit before it contributes to a dot product. Storage capacity tells you what fits; traffic tells you how many bytes cross a boundary. They answer different questions.

The storage names in the path

  • Registers: working values for an individual thread, such as a running sum, stored on the SM.
  • Shared memory: storage on the SM that threads in one block explicitly fill and reuse.
  • L1 and L2 caches: hardware-managed stores of recently used data. L1 is associated with an SM; L2 is shared across the device. A cache hit can avoid fetching data from device memory.
  • Device DRAM: the GPU’s main memory for allocations such as inputs and weights. HBM means high-bandwidth memory, one DRAM technology used by many datacenter GPUs. Global memory names the address space used to access these allocations.

The transformer KV cache is a software data structure, usually allocated in global memory. It is different from the hardware L1/L2 caches. A load reads a value; a store writes one. A multiply-add multiplies two operands and adds their product to a running sum.

One operand: storage scopes and optional staging

Compare a global load used directly by a thread with a tiled kernel that explicitly stages operands in shared memory. These are storage scopes, not a mandatory hardware route. Exact cache and instruction paths vary by hardware.

Global load

Inputs and weights occupy global allocations backed by device DRAM, often HBM on datacenter GPUs. Hardware caches such as device-wide L2 and SM-local L1 can serve loads: a cache hit can avoid a DRAM fetch. Not every instruction uses every cache.

Optional shared-memory staging

A tiled kernel can cooperatively load operands into block-local shared memory for reuse. A block barrier makes the staged values safe to consume; another barrier is needed before overwriting values still in use. A direct per-thread load can skip this staging.

Per-thread computation

Threads use operands in registers and update their multiply-add accumulators. In the tiled example, threads read the staged shared-memory values first. Registers are per-thread working storage, not shared addressable storage.

Output store

Completed results are stored to global memory through the applicable store/cache path. This does not imply each store immediately writes HBM.

Choose a memory boundary before counting traffic. Shared memory is explicitly managed block-local storage; hardware caches are managed by hardware. Reuse can reduce global-load demand. Capacity, logical requests and actual DRAM traffic remain different quantities.

Spills, hardware variation and unified memory

Excess register demand can spill into thread-local memory backed by device memory. Shared-memory bank conflicts (competing accesses to the same storage bank) and synchronization affect access cost. Exact cache paths and capacities vary by architecture.

A software KV cache need not fit in hardware L2. Apple unified memory changes the physical organization; these capacity/traffic distinctions still help, while CUDA block and warp details do not transfer verbatim.

Neighboring lanes, neighboring addresses

If adjacent lanes request nearby addresses, hardware can service them with fewer memory sectors. Change the address stride before predicting how much useful data each sector carries.

Stride is the distance between neighboring lanes’ addresses, measured here in 4-byte elements: stride 1 steps 4 bytes, stride 8 steps 32 bytes. A sector is a 32-byte address region in this teaching model: bytes 0–31, then 32–63, and so on.

Alignment describes where the first address falls relative to a sector boundary. Starting byte offset 0 begins on a boundary; offset 4 begins four bytes later. Coalescing means combining a warp’s nearby memory requests into fewer transactions. Here we count touched sectors, not measured DRAM traffic.

Inspect a warp’s memory requests

Toy transaction model: 32 lanes each load one distinct 4-byte number; 32-byte aligned sectors, no cache reuse. Stride 1 from byte 0 touches 4 sectors (128 bytes); stride 8 touches 32 sectors (1,024 bytes) for the same 128 useful bytes.

Define the boundary before counting

This explorer counts distinct 32-byte sectors touched by one warp instruction. It does not predict HBM transactions, cache hit rate, latency or speedup. Real transaction rules depend on instruction width, alignment and GPU architecture. The byte offset changes alignment; stride is measured in elements, not bytes. The requested addresses remain distinct in this example.

Reusing bytes takes coordination

Several threads can reuse an operand loaded into shared memory. They must wait until the cooperative loads finish, then wait again before overwriting a tile still in use. Faster memory without correct synchronization is a race, not an optimization.

A tile is a small portion of a matrix loaded for reuse. A block barrier is a synchronization point: participating threads wait until the block has reached it and prior shared-memory writes are available to them. This makes a cooperative load safe to reuse. It coordinates threads within a block, not separate blocks.

Cooperative loadThreads load different tile elements into block-shared storage.
Block barrierEnsure all required values are available before consuming them.
Reuse, then barrierAccumulate with the tile. Ensure consumers finish before the next tile overwrites it.

Ordinary block barriers must be reached by all participating threads consistently. Guard out-of-range loads and stores, not the barrier itself. Separate blocks cannot use an ordinary block barrier to communicate.

Capacity, traffic, bandwidth, latency

Capacity uses bytes; bandwidth uses bytes/second; latency uses seconds per dependent access. A 1 GiB tensor read ten times can create about 10 GiB of logical reads while occupying only 1 GiB. Hardware caches may reduce HBM reads. Shared-memory reuse can reduce global-load demand while consuming scarce on-chip storage. Lower HBM traffic does not guarantee lower time when another resource becomes limiting.
